# Locked Control Lab compute profiles — #163

This is the first API increment, not completion of #163. It extends the existing
AppStore preparation job and Control Lab ExperimentStore/Attempt. There is no new
execution queue, approval service, or EnvironmentUse coordinator.

## Delivered behavior

- An explicit `create_locked_control` request creates an independent scientific
  recipe from Control Lab's validated manifest pins. Existing App environments,
  App bindings, micromamba and App preparation remain unchanged.
- Explicit Prepare uses official uv **0.12.20** archives and executable SHA-256
  pins; it never chooses a PATH uv. CPython **3.12.14**, build **20260924**, is
  selected from that release's fixed download table. The receipt distinguishes
  requested Python, source archive URL/SHA, observed build/platform/executable,
  native `uv.lock` digest, uv identity and actual installed distribution content.
- First Prepare resolves a complete native lock from `https://pypi.org/simple`.
  Retry and `rebuild` use the saved lock with `uv sync --locked --no-build`.
  No source builds, editable projects, arbitrary project hooks or custom indexes.
- A new prefix stays unpublished until imports and observations succeed. Its
  physical path never moves (venv scripts contain absolute prefixes); an atomic
  catalog write publishes it. Published profiles cannot be prepared in place.
  Rebuild copies verified project/lock bytes to a new record and prefix.
- Preparation uses an OS lock. Failures retain the existing Failed/log contract;
  Host restart marks unfinished jobs Failed. Explicit retry cleans only that
  record's unpublished generations. Ready profiles and historical outputs remain.
- `bind_compute` writes a Host-owned selection in Control Lab App data. It does
  not touch App Python settings, restart the backend, or start an experiment.
  Legacy `list` excludes compute profiles so existing App-wide binding controls
  cannot accidentally select one. `list` with `compute:true` returns them.
- The original calculation owner freezes the selected profile at operation
  admission. It uses a fixed Python child entrypoint, validates the observed
  interpreter/packages and distribution bytes, and owns stop/reaping through its
  existing cancellation event. Changed selection requires a new experiment;
  old results are never refrozen. Snapshot JSON, actual environment observation,
  logs and solver results are hashed by the existing trial/export ledger.

The source archive SHA identifies the downloader input; the executable SHA is a
separate observation. Distribution identity hashes installed files listed with
hashes in RECORD, excluding generated bytecode and prefix-specific external CLI
launchers. This is not a full filesystem attestation or numerical equivalence claim.

## Host API

Use the enabled Environments App's existing `environments` grant. The outer JSONL
request is `{"method":"apps","id":"request-id","action":"localenvironment",
"name":"environments","request":{...}}`.

| Request | Result |
| --- | --- |
| `{"operation":"create_locked_control","label":"Control CPU"}` | New record; no download |
| `{"operation":"prepare","id":"env-…"}` | Explicit preparation; returns compute records |
| `{"operation":"list","compute":true}` | Read-only persisted state and receipts |
| `{"operation":"bind_compute","id":"env-…"}` | Select verified compute prefix; no App restart |
| `{"operation":"rebuild","id":"env-…","label":"Control rebuilt"}` | New record with the exact source lock; Prepare explicitly |

Start computation through the existing Control Lab Goal/experiment routes.
There is no new scientific dispatch API. Unbinding to service Python is not yet
exposed; select another prepared profile and create a new experiment.

## Reproduce the local gates

Use a fresh absolute evidence directory; these opt-in commands download uv,
Python and PyPI wheels. The test retains evidence rather than deleting it.

```sh
PERO_UV_LIVE_HOME=/absolute/fresh/evidence node scripts/cargo.mjs test -p pero-runtime --lib locked_control_rebuild_and_recovery -- --ignored --nocapture
python3.14 scripts/verification/uv-control.py /absolute/fresh/evidence
PERO_APP_PYTHON=/absolute/python3 node scripts/cargo.mjs test -p pero-runtime --lib
node scripts/cargo.mjs build -p pero-host
node scripts/codegen/contracts.mjs --check
```

The Python acceptance launches a real service using the invoking interpreter and
real numerical children using the prepared one. It checks the same backend PID,
PI analytic reference, changed binding, missing dependency, same-version library
byte drift, retained exports and actual cancellation. Its binding writes replay
Host-published profile values inside the disposable test home; preparation and
binding authority are separately exercised through real AppStore in Rust.

Run the existing Python suite using the prepared profile's `bin/python`:
`-m unittest discover -s apps/control-lab/test -p 'test_*.py'`.
Using macOS's `/usr/bin/python3` selected Xcode Python 3.9 and failed on the
repository's Python 3.10+ syntax. Homebrew 3.14 without scientific dependencies
also cannot run existing real ngspice/numpy tests. These are test prerequisites,
not reasons to silently change the service or scientific interpreter.

## Remaining boundaries

- UI creation/selection, Electron/Native observations and signed packages have
  not been delivered or claimed. Existing visual controls are unchanged.
- No production EnvironmentUse admission/lease/release wiring. The receipt is
  software evidence linked through the existing attempt's artifact ledger, not
  an Owner grant. Existing Goal approval remains; full profile-aware approval
  presentation belongs to the subsequent UI/Use increment.
- PC-Gym, ngspice executable binding, adopted/Conda environments, arbitrary repo
  discovery/proposals, native ABI/GPU/HPC remain outside this fixed Control recipe.
- Linux x86_64 has pinned assets but no live runner evidence here. Windows,
  macOS x86_64 and other architectures are explicitly unsupported by this path.
- No preparation cancellation API, network-outage acceptance, hard-kill child
  reconciliation or multi-Host acceptance. Scientific child cancellation is
  separately verified. Interrupted unpublished prefixes are removed on explicit
  retry, not by automatic scientific replay or background garbage collection.
- Existing App service preparation still has its older uv/PATH behavior; the
  verified downloader here applies only to the new locked compute path.

## Pixi fixed-source study

Reviewed **Pixi v0.84.2**, commit
[`98cc736a9ba6e7e15f19abd59ff45ba805f712bd`](https://github.com/prefix-dev/pixi/tree/98cc736a9ba6e7e15f19abd59ff45ba805f712bd),
not an unpinned latest document. Its
[install adapter](https://github.com/prefix-dev/pixi/blob/98cc736a9ba6e7e15f19abd59ff45ba805f712bd/crates/pixi_cli/src/install.rs)
and [lock semantics](https://github.com/prefix-dev/pixi/blob/98cc736a9ba6e7e15f19abd59ff45ba805f712bd/docs/workspace/lock_file.md)
support preserving native `pixi.lock`, checking manifest consistency with
`install --locked`, and selecting one environment/platform. Default install/run
may update or prepare environments; do not use that implicit behavior at read or
scientific dispatch boundaries.

This revision's [system requirements](https://github.com/prefix-dev/pixi/blob/98cc736a9ba6e7e15f19abd59ff45ba805f712bd/docs/workspace/system_requirements.md)
have moved toward per-platform virtual-package declarations. Old generic
`[system-requirements]` examples must not be copied uncritically. CUDA solver
constraints still do not constitute an observed GPU or driver grant.

A possible second adapter should be driven by a real Conda/PyPI/native conflict
(e.g. ngspice or PC-Gym native dependencies), accept a reviewed manifest/lock,
prepare software, and return source/observation evidence to the existing Host
and Environment owner. It must not call Pixi tasks as a replacement scheduler.
No Pixi executable was installed, no native compatibility was accepted, and no
provider interface was added before a second real implementation exists.
