For example, a project link to a Paper report opens the original in Paper. To record the data you reviewed at that point, note the exact Data file version or save a Notebook revision with a reference.

Trace a conclusion back to evidence

  1. Find the source. Follow a paper claim to the cited passage and check the context and units. For data, identify the exact file version, source, and SHA-256.
  2. Find the run. Check the input, method version, parameters, and environment. Open the logs and artifacts from that attempt. Keep the earlier attempt available when you rerun for comparison.
  3. Read the verification verdict. Check which output was evaluated, what rule was fixed before the run, and what an independent check recomputed. Record whether verification passed, found a mismatch, or was unavailable. A completed run establishes that the procedure ran.
  4. State the scope. The Fisher example checks one value in Table III. REPRODUCED applies to that value. The whole-paper verdict is NOT_ASSESSED.

A useful record for Fisher (1936) names the Table III result, the 100 reviewed inputs, the expected 19.1434 cm², and the tolerance of 0.00005 cm². The exported verification report contains the independent check.

Local data, permissions, and billing

  • Settings and data. The default Electron workbench stores Host settings in ~/.pero/config/runtime-settings.json and App records in ~/.pero/app-data/. Conversation history is in sessions.jsonl in Electron’s user-data directory. Native, standalone products, and isolated development profiles use their own locations.
  • External requests. Reading a local file and running a local method can stay on your computer. Model requests, literature search, MCP, and shared task services may receive relevant questions, selected context, or tool arguments. Review drafts, attachments, and requested permissions before proceeding.
  • Billing. Model and compute charges come from the provider’s usage records. Workflow step and time limits govern that execution. The interface shows usage when usage data is available.

Use App export actions to share research records. Dataset versions, notebook revisions, and run evidence have their own export formats and scopes.

Read acceptance records and diagnose problems

Identify where the failure occurred. Start with startup troubleshooting if the workbench or an App cannot launch. For model errors, check sign-in, credentials, and session settings. When a submitted job produces no result, check the connection, attempt state, logs, and artifacts. If the conclusion is in question, follow the source and verification checks.

The acceptance levels describe the conditions covered. L0 covers code and contract checks. L1 runs Desktop with an Agent fixture. L2 uses a real provider, environment, or service. L3 checks installation, upgrade, and operation of the signed package on the target system. Check the version, platform, sample, and remaining gaps in each record.

When filing a GitHub issue, include the version or commit SHA, OS and architecture, Electron or Native, steps, expected and observed results, and any shareable error or request ID.
