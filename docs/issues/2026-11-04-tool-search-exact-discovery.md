# Deferred ToolSearch cannot reliably find known tool names

An opt-in coding benchmark using the existing deferred tool profile searched for
`files terminal list read write` and `read file contents`. Both searches returned
zero tools because keyword discovery requires every literal word to occur in one
name/description. A later `terminal` search loaded PTY tools; the run then spent
30 TerminalOpen and 31 TerminalRead calls and exhausted its 64-request budget.
This is an observed discovery and tool-selection failure, not evidence that
smaller schemas improve total tokens or task quality.

Even a query containing the full name `Read` can omit that tool from the default
first page: other descriptions contain “read” and alphabetical ordering puts
five such tools first. The zero-result response also reused a generic activation
notice instead of explaining that nothing had been activated or how to recover.

The fix belongs to native ToolSearch matching and its own descriptions/results.
Keep literal AND keyword search, prioritize a full exact tool name, and add
`select:Name1,Name2` to select known names from the already caller-authorized
candidate set. Keep the existing pagination, schema budget, exact-version
activation and dispatch owners. No semantic/fuzzy search or permission change is
introduced.

## Verification

`go -C harness/go test -race ./nativetools`, package `go vet` and `git diff
--check` passed. Matching cases cover full-name priority, case-insensitive exact
selection, duplicate/unknown names, literal AND behavior and zero-result
recovery. Caller restriction and unregistration checks run against keyword,
full-name and select queries. Pagination/budget cases also run with select;
an oversized selected schema is omitted and cannot dispatch. Existing wire
tests still exercise same-batch rejection, withdrawal, rediscovery, disk resume
and child isolation.

A separate rebuilt ACP binary ran against loopback with the two original failed
queries, followed by `select:Read,Write` and a real Read. Request tool counts
were `1,1,1,3,3`; the failed searches activated nothing, both returned recovery
instructions, and the selected schemas reached the next request. Actual file
content then reached the final provider request. All five HTTP requests were
local fixtures with synthetic usage, no paid model calls; shutdown succeeded.
Evidence is in the local coding-benchmark report's
`tool-search-selection-probe/results.json`, generated by
`probe_tool_search_selection.py`.

The original benchmark binary, frozen runners and raw Session/results files
were not modified. The probe scripts the recovery query; it does not prove a
real model will choose it or improve tokens, latency or coding quality. The
ordinary multiword queries deliberately retain their documented AND semantics.
