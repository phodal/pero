# Deferred ToolSearch cannot reliably find known tool names

## Follow-up: exact names activate unrelated tools and repeat schemas

The latest React Session searched `TaskStop` and also activated Agent and Bash
because their descriptions mention that name. Agent then remained declared for
31 replies without being invoked. Full-name queries must return only the exact
caller-visible tool; keyword and explicit multi-name selection retain their
existing behavior.

Five discovery receipts also repeated 20,278 UTF-8 text bytes of descriptions
and schemas in model history, in addition to the following declarations.
Deferred discovery will keep its complete bounded receipt in durable metadata
and return a compact activation receipt to the model. Preserve schema hashes,
omitted-schema recovery, pagination and the existing activation authority.
Non-deferred discovery continues returning tool schemas.

Verification pending: matching tables, actual HTTP request declarations and
model-visible receipts, withdrawal/rediscovery/resume, package race and vet.

## Follow-up: explicit selection truncated by keyword default

The live React rerun selected `Read,Write,Edit,Bash,Glob,Grep`. All six
matched, but the shared default page size returned only five and omitted
Write. The model did not request the continuation and repeatedly used Bash
to write source. Exact selection should default to the existing maximum of
20 schemas; keyword queries keep their five-result default. Explicit limits,
the 32 KiB schema budget and activation checks still apply. This removes an
observed discovery obstacle; it does not by itself prove token savings.

Verification: the matching table now includes seven exact names. Page-size
cases cover the unchanged keyword default of five, the exact-selection cap of
20 and an explicit limit of two. Existing oversized-schema and continuation
cases still cover both query modes. `go test -race ./nativetools` and
`go vet ./nativetools` pass.

An opt-in coding benchmark using the existing deferred tool profile searched for
`files terminal list read write` and `read file contents`. Both searches returned
zero tools because keyword discovery requires every literal word to occur in one
name/description. A later `terminal` search loaded PTY tools; the run then spent
30 TerminalOpen and 31 TerminalRead calls and exhausted its 64-request budget.
This is an observed discovery and tool-selection failure, not evidence that
smaller schemas improve total tokens or task quality.

Even a query containing the full name `Read` can omit that tool from the default
first page: other descriptions contain “read” and alphabetical ordering puts
five such tools first. The zero-result response also reused a generic activation
notice instead of explaining that nothing had been activated or how to recover.

The fix belongs to native ToolSearch matching and its own descriptions/results.
Keep literal AND keyword search, prioritize a full exact tool name, and add
`select:Name1,Name2` to select known names from the already caller-authorized
candidate set. Keep the existing pagination, schema budget, exact-version
activation and dispatch owners. No semantic/fuzzy search or permission change is
introduced.

## Verification

`go -C harness/go test -race ./nativetools`, package `go vet` and `git diff
--check` passed. Matching cases cover full-name priority, case-insensitive exact
selection, duplicate/unknown names, literal AND behavior and zero-result
recovery. Caller restriction and unregistration checks run against keyword,
full-name and select queries. Pagination/budget cases also run with select;
an oversized selected schema is omitted and cannot dispatch. Existing wire
tests still exercise same-batch rejection, withdrawal, rediscovery, disk resume
and child isolation.

A separate rebuilt ACP binary ran against loopback with the two original failed
queries, followed by `select:Read,Write` and a real Read. Request tool counts
were `1,1,1,3,3`; the failed searches activated nothing, both returned recovery
instructions, and the selected schemas reached the next request. Actual file
content then reached the final provider request. All five HTTP requests were
local fixtures with synthetic usage, no paid model calls; shutdown succeeded.
Evidence is in the local coding-benchmark report's
`tool-search-selection-probe/results.json`, generated by
`probe_tool_search_selection.py`.

The original benchmark binary, frozen runners and raw Session/results files
were not modified. The probe scripts the recovery query; it does not prove a
real model will choose it or improve tokens, latency or coding quality. The
ordinary multiword queries deliberately retain their documented AND semantics.

## Follow-up: live natural-language queries still return nothing

Each of the three later QuixBugs tasks made an empty keyword search before
recovering. Exact-name selection does not help a caller that describes a
capability instead of knowing its registered name. Pi's local tool-search
implementation ranks partial keyword coverage over authorized metadata.

Prefer the existing all-word matches. Only when there are none, return bounded
partial keyword matches ranked by coverage and name matches, with an explicit
partial-match notice. Preserve exact selection, caller filtering, schema budget,
pagination and exact-version activation. Do not invent aliases or add an
embedding service. Verify recovery through actual provider declarations and
denied/retired-tool cases before running another model sample.

Verification: full Harness Go race tests (35 packages), `go vet ./...` and
`git diff --check` pass. Matching tables cover full-match preference, partial
ranking, exact-name misses and unchanged bounds. The real HTTP-wire rediscovery
case now uses a partial query, then verifies the exact tool declaration and
successful invocation on the next provider request. Restricted/retired tools
remain absent. See [source comparison and live follow-up](../fitness/dsh-native-improvements.md).
