从结论回查来源和验证

  1. 定位来源。论文主张回到引用段落，检查上下文和单位。数据回到明确的文件版本，查看来源和 SHA-256。
  2. 找本次运行。对照输入、方法版本、参数和环境，打开同一次尝试的日志与产物。重新运行时记录新的尝试，保留旧结果以便比较。
  3. 读验证结果。确认检查针对哪个输出、用什么预先定义的规则、哪部分由独立过程复算。执行正常只能证明运行完成。验证未执行、验证不匹配和已通过验证需要分别理解。
  4. 写明结论范围。例如，Fisher 案例复核的是 Table III 的一个数值。REPRODUCED 是该数值的判定，整篇论文仍为 NOT_ASSESSED。

例如，Fisher（1936）的复核记录应写明 Table III 的具体条目、100 条核对过的输入、预期值 19.1434 cm² 和容差 0.00005 cm²。独立检查结果见导出的验证报告。

本地数据、权限与费用

  • 配置和数据。默认 Electron 工作台把 Host 设置保存在 ~/.pero/config/runtime-settings.json，把 App 记录保存在 ~/.pero/app-data/。会话历史保存在 Electron 用户数据里的 sessions.jsonl。独立产品、Native、开发和隔离配置的位置应按各自说明确认。
  • 外部请求。直接阅读本地文件和运行本地方法可以在本机完成。使用模型、文献搜索、MCP 或共享任务服务时，所选问题、上下文或工具参数可能发给相应服务。发送前可以检查草稿及附件，执行前查看实际请求和会话权限。
  • 费用。模型和远程算力以供应方的用量记录计费。工作流的步骤或时长限制约束本次运行的行为。界面只在收到用量数据时展示对应数据。

交换研究记录时优先使用 App 的导出入口。版本对照、Notebook 修订和运行证据都有自己的导出范围，详见相应用法。

读懂验证记录并排查故障

先定位故障发生在哪一层。桌面或 App 无法启动，从安装排错开始。模型无法回复，看登录、凭据和会话设置。任务已提交但没有结果，检查连接、尝试状态、日志和产物。结果有疑问，从来源与验证回查。

验收分级以证据覆盖的条件为准。L0 是源码检查，L1 是实际桌面配测试 Agent，L2 涉及真实提供方、环境或外部服务，L3 是签名发布包在目标系统上的安装、升级和运行。查看记录时同时核对版本、系统、样例与未覆盖范围。

向 GitHub Issues 提交问题时，附上版本或提交 SHA、操作系统和架构、Electron 或 Native、可复现步骤、预期与实际结果，以及可公开的错误和请求 ID。
